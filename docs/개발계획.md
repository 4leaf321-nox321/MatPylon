## 0. 이 앱이 하는 일과 하지 않는 일

**한다** — 파일을 정확한 자리에, 한 번만, 안전하게 배달한다.

- 소스 폴더 여러 개를 감시한다 (장비 하나 = 소스 하나, PC 하나에 장비 여럿 가능)
- 쓰기가 끝난 파일만 집는다
- 같은 내용은 두 번 보내지 않는다
- 정해진 주기(기본 1시간)에 모아 보내고, 실패는 남겨 두었다가 다시 보낸다
- 파일명·파일 메타에서 **힌트**(재료 코드·시료·시편)를 뽑아 함께 보낸다
- 자기 상태(마지막 전송·대기·실패)를 서버에 보고한다

**하지 않는다**

- **파일을 파싱해서 곡선을 만들지 않는다.** 그것은 MatNexus 의 일이다
  (ADR 0005 형식 프로파일, ADR 0017 "곡선을 API 로 직접 꽂지 않는다").
  클라이언트가 파싱하면 프로파일 지식이 두 벌이 된다.
- **시편을 만들지 않는다.** 힌트가 시편에 닿지 않으면 서버 수집함에 대기하고
  사람이 붙인다. 오타 하나가 유령 시편을 만드는 병을 MatNexus 가 이미 겪었다.
- **원본을 지우거나 옮기지 않는다** — 기본값은. 원장(로컬 DB)에만 기록한다.
  이동은 소스별 옵션이다(장비 소프트웨어가 자기 파일을 다시 여는 경우가 있다).

### 프로세스 구조

```
electron main
 ├─ engine/           ← Electron 을 모르는 순수 Node. 서비스 모드가 오면 이것만 떼어 낸다
 │   ├─ sources/      소스 폴더 스캔·안정화·해시
 │   ├─ ledger/       SQLite 원장 (파일 상태 기계)
 │   ├─ hints/        파일명 규칙 → 힌트
 │   ├─ transport/    MatNexus API 클라이언트 (PAT, 재시도, 오류 엔벨로프 해석)
 │   ├─ scheduler/    주기 실행
 │   └─ heartbeat/    상태 보고
 ├─ ipc/              렌더러 ↔ 엔진 (contextBridge, 타입 있는 채널)
 └─ tray/             트레이 아이콘·메뉴·알림
renderer (React)      설정 화면. 엔진 상태를 IPC 로 구독
```

`engine/` 이 `electron` 을 import 하면 아키텍처 테스트가 막는다 — MatNexus 의
"`matcore` 는 DB·HTTP 를 모른다" 와 같은 장치다.

## 3. 파일 상태 기계 (원장)

```
seen ──안정화──▶ ready ──전송 시도──▶ sending ──2xx──▶ sent
                  │                     │
                  │                     ├──4xx(재시도 무의미)──▶ failed   ← 사람이 본다
                  │                     └──5xx/네트워크──▶ retry(n) ──▶ ready (백오프 후)
                  │
                  └──내용 해시가 sent 에 이미 있음──▶ duplicate
```

원장 행: `path, size, mtime, sha256, status, attempts, last_error, server_run_id,
inbox_id, source_id, first_seen_at, sent_at`.

- 경로가 아니라 **해시가 정체**다. 같은 파일을 다른 이름으로 복사해도 한 번만 간다.
- 서버가 "이미 있다"(409 + 기존 id)를 돌려주면 `sent` 로 닫는다 — 서버 원장이 정본.
- 재시도 백오프: 1분·5분·15분·1시간 → 이후 주기마다. 최대 횟수 없음(폐쇄망은 며칠
  끊길 수 있다). 4xx 는 즉시 `failed`.
- 원본을 옮기는 옵션은 `sent` 가 된 **뒤에만** 실행한다.

## 4. 힌트 추출 (C 결정)

클라이언트는 **확정하지 않고 힌트만 보낸다.** 세 단계 중 앞 둘은 클라이언트,
셋째는 서버.

1. **파일명 규칙** — 소스별 정규식, 이름 있는 그룹으로 힌트를 뽑는다.
   ```
   ^(?<material>[A-Z0-9-]+)_(?<lot>[^_]+)_(?<specimen>[A-Z]{2}-?\d+)\.tra$
   ```
   GUI 에서 실제 폴더의 파일 이름 20개로 **미리보기** — 어느 파일이 어느 그룹으로
   잡히는지 표로 보여 준다. 맞지 않는 파일은 힌트 없이 간다(막지 않는다).
2. **파일 메타** — 서버가 프로파일 `identity` 규칙(ADR 0018)으로 한다. 클라이언트는
   안 한다.
3. **수집함** — 둘로도 시편이 하나로 정해지지 않으면 서버 `inbox` 에 대기. 사람이
   MatNexus 화면에서 시편을 고르면 그때 `TestRun` 이 된다.

힌트 키는 고정한다: `material_code · lot · specimen · orientation · tested_at ·
operator · instrument`. 정규식 그룹 이름이 이 집합 밖이면 GUI 가 경고한다.

## 5. MatNexus 에 만들 API (계획 — 이쪽이 정하고 저쪽이 만든다)

기존 규약을 그대로 따른다: 성공은 리소스 그대로, 오류만 `{error:{code,message,
request_id,details}}`, 코드 `MNX-PIPE-NNNN`, 인증은 PAT Bearer. 모듈 이름은
`pipelines`(개발계획 §구조에 이미 예약된 이름).

### 5.1 커넥터 (장비 PC 등록)

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| `POST` | `/api/pipelines/connectors` | 등록. `{name, hostname, workspace_id}` → `{id, ...}`. PAT 소유자의 부서 안에서만 |
| `GET` | `/api/pipelines/connectors` | 목록(관리 화면). 마지막 heartbeat·대기·실패 수 포함 |
| `PATCH` | `/api/pipelines/connectors/{id}` | 이름·활성 여부 |
| `POST` | `/api/pipelines/connectors/{id}/heartbeat` | `{app_version, sources:[{key, pending, failed, last_sent_at}], next_run_at}` → 서버 시각·설정 힌트(업로드 한도 등) 응답 |

### 5.2 반입 (파일 배달)

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| `POST` | `/api/pipelines/inbox` | multipart: `file`, `connector_id`, `source_key`, `client_sha256`, `client_path`, `mtime`, `hints`(JSON). 응답 `202 InboxItemOut` |
| `GET` | `/api/pipelines/inbox` | 목록. 상태 `received · parsed · needs_specimen · registered · failed`. 페이지·필터 |
| `GET` | `/api/pipelines/inbox/{id}` | 상세 — 파싱 결과 요약·추정한 시편 후보·오류 |
| `POST` | `/api/pipelines/inbox/{id}/assign` | `{specimen_id, test_type?}` — 사람이 붙인다 → `TestRun` 생성 |
| `POST` | `/api/pipelines/inbox/{id}/discard` | 버린다(사유 필수) |
| `POST` | `/api/pipelines/inbox/{id}/retry` | 프로파일을 고친 뒤 다시 파싱 |

서버 쪽 처리 순서(워커):
1. 원본을 `filestore/inbox/YYYY/MM/<id>/` 에 저장, sha256 검증(클라이언트 값과 다르면 `MNX-PIPE-0003`)
2. 같은 sha256 의 `TestRun` 이나 `InboxItem` 이 있으면 **409 + 기존 id** (클라이언트는 `sent` 로 닫는다)
3. `/test-types/detect` 와 같은 지문으로 프로파일·시험 종류 추정
4. 프로파일로 파싱 → `identity` + 클라이언트 `hints` 로 재료·시료·시편 후보 조회
5. 후보가 **정확히 하나**면 `TestRun` 생성(기존 업로드 경로 재사용, 원본 이동), `registered`
6. 0 또는 2 이상이면 `needs_specimen` — 알림(기존 notifications 모듈)

## 7. 설치·배포

- `MatPylon-Setup-x.y.z.exe` 하나. per-user 설치, 관리자 권한 불필요.
- 설치 직후 첫 실행에서 **설정 마법사**(서버 URL → PAT → 커넥터 이름 → 첫 소스).
- 설정·원장·로그는 `%APPDATA%\MatPylon\` — 재설치·갱신해도 남는다.
- 코드 서명은 하지 않는다(사내 배포). SmartScreen 경고 안내를 README 에 적는다.
- 갱신: 1차는 설치파일 재실행(설정 유지). 2차에 MatNexus `/api/pipelines/releases`
  에서 새 버전을 알려 주고 GUI 가 안내 — 폐쇄망이라 GitHub 갱신은 쓸 수 없다.

| **P4 계약 확정** | §5 를 OpenAPI 문서(`docs/api/matpylon-openapi.yaml`)로 고정 → MatNexus 에 전달 | 양쪽이 같은 파일을 본다 |
| **P5 실연결** | MatNexus 에 `pipelines` 모듈이 생기면 실서버로 한 바퀴 — 파일 → 수집함 → 시편 붙임 → 곡선 | 실제 장비 파일로 확인 |

P2 까지는 MatNexus 없이 진행한다. **P4 의 OpenAPI 문서가 두 프로젝트 사이의
계약**이고, MatNexus 는 그 문서대로 만든 뒤 `export_openapi.py` 결과가 그것과
맞는지 CI 에서 대조한다.

## 9. 열린 항목 (실물이 있어야 정해진다)

- 실제 장비 파일의 크기·개수·생성 빈도 — I(청크 업로드) 결정의 근거
- 장비 소프트웨어가 파일을 한 번에 쓰는지, 임시 이름으로 썼다가 바꾸는지 — E 의 기본값
- 장비 PC 가 네트워크 드라이브에 쓰는 경우가 있는지 — chokidar 가 못 보므로 스캔 주기
- 부서 하나에 장비 PC 가 몇 대인지 — 설정 복제 기능의 우선순위
